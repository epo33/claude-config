# Defining Services

A service is a method that a client can call over HTTP and that server code can call directly. You write services in Dart mixins. Sing reads them when it generates the model, then generates the server dispatch code and the client API.

## 1. Before You Start

Services use code generated by Sing (`Order`, `$Order`, `Order$Search`, ...). The generated code must match the model before you write or change a service.

- If you changed an entity, a field or a namespace, run `dart run sing_builder:sing_emit` from the model package first.
- `sing_emit` rewrites only the files whose content changes. The modification date of `model/lib/sing/server.dart` therefore does not show that a build ran. Each run touches `model/.dart_tool/sing_regen.done`. If a model file is newer than this file, the model was not rebuilt.
- When `sing_emit` reports `[error]` diagnostics, it writes no file at all. `--force` writes the files anyway (the run still fails). Use it only to understand the problem, then regenerate without it.

## 2. Where Services Come From

An entity or a namespace gets services in three ways:

| Source | How to declare it | Section |
| --- | --- | --- |
| Standard CRUD services | `@StdEntityServices()`, `@LoadServices()`, ... on the entity | [3](#3-standard-crud-services) |
| Search service | `@Searchable()` on the entity | [SEARCHES.md](SEARCHES.md) |
| Custom services | `@Implementor(SomeMixin)` on the entity or namespace | [4](#4-custom-services-on-an-entity) and [5](#5-custom-services-on-a-namespace) |

The generator stacks all of them into one generated class per entity, for example:

```dart
// model/lib/sing/order_hub/orders/order.dart (generated)
class Order$Services extends sing.EntityServerServices<Order, String>
    with Order$SearchMixin<Order, String>,   // from @Searchable()
         model.OrderServices,                // from @Implementor(OrderServices)
         sing.LoadServicesMixin<Order, String> { ... } // from @LoadServices()
```

The client package gets a class with the same name and the same services, without the `callContext` parameter.

## 3. Standard CRUD Services

### 3.1. Annotations

All annotations are in `sing_server/lib/src/std_services/`.

| Annotation | Services added |
| --- | --- |
| `@StdEntityServices()` | all of the services below |
| `@LoadServices()` | `loadThisKey`, `loadThoseKeys`, `loadThisRef`, `loadThoseRefs` |
| `@InsertServices()` | `insertThis`, `insertThose` |
| `@UpdateServices()` | `updateThis`, `updateThose` |
| `@UpsertServices()` | `upsertThis`, `upsertThose` |
| `@DeleteServices()` | `deleteThisKey`, `deleteThoseKeys`, `deleteThisRef`, `deleteThoseRefs` |

`@StdEntityServices` options:
- `delete`, `insert`, `load`, `update`, `upsert` (`bool`, default `true`): turn one group off, e.g. `@StdEntityServices(delete: false)`.
- `accessToken`: token for every service. `readToken` (load) and `writeToken` (insert, update, upsert, delete) override it.
- `serverSideOnly: true`: the services exist on the server but are not published to clients.

The single annotations (`@LoadServices()`, ...) take `serverSideOnly` and `accessToken`.

### 3.2. Signatures

Server side (`E` is the entity type, `PK` its primary key type). Every method returns a `DataLoader<E>`:

```dart
DataLoader<E> loadThisKey({required CallContext callContext, required PK key});
DataLoader<E> loadThoseKeys({required CallContext callContext, required Iterable<PK> keys});
DataLoader<E> loadThisRef({required CallContext callContext, required Reference<E> ref});
DataLoader<E> loadThoseRefs({required CallContext callContext, required Iterable<Reference<E>> refs});
DataLoader<E> insertThis({required CallContext callContext, required DataRow<E> data});
DataLoader<E> insertThose({required CallContext callContext, required Iterable<DataRow<E>> data});
DataLoader<E> updateThis(...data: DataRow<E>);   DataLoader<E> updateThose(...data: Iterable<DataRow<E>>);
DataLoader<E> upsertThis(...data: DataRow<E>);   DataLoader<E> upsertThose(...data: Iterable<DataRow<E>>);
DataLoader<E> deleteThisKey(...key: PK);          DataLoader<E> deleteThoseKeys(...keys: Iterable<PK>);
DataLoader<E> deleteThisRef(...ref: Reference<E>); DataLoader<E> deleteThoseRefs(...refs: Iterable<Reference<E>>);
```

The client methods are the same without `callContext` (`sing_client/lib/src/std_services.dart`).

Behavior to know:
- The `DataLoader` does nothing until you run it (`exactlyOne()`, `listValues()`, `execute()`, ...). See [DATA_CLASSES.md](DATA_CLASSES.md).
- Insert, update and upsert clear the values of read-only fields before writing. Code that writes through `$query` directly is not affected.
- The standard services run the [entity change listeners](#7-entity-change-listeners).

## 4. Custom Services on an Entity

### 4.1. Set Up the Mixin

Example with the `Order` entity of OrderHub.

1. Create `order.services.dart` next to `order.dart`:

```dart
import "package:model/model.dart";
import "package:model/sing/server.dart";

mixin OrderServices on EntityServerServices<Order, String> {
}
```

2. Declare the mixin on the entity, and export the services file:

```dart
// order.dart
import "package:model/model.dart";

export "order.services.dart";

@Implementor(OrderServices)
@LoadServices()
@Searchable()
class OrderEntity extends ModelEntity with UuidPrimaryKeyMixin {
  // ...
}
```

3. Regenerate the model. Then add methods to the mixin.

The two type arguments of `EntityServerServices<E, PK>`:
- `E` is the generated entity type (`Order`), **not** the model class (`OrderEntity`). It is declared in `common/lib/src/sing/common.dart`, or in `model/lib/sing/server_common.dart` for a `@serverSideOnly` entity.
- `PK` is the primary key type. Read it in the generated `class _Order$Impl extends sing.ServerEntityDef<Order, String>`: it is the second type argument. Use `Object` for an entity without primary key.

`@Implementor` options: `serverSideOnly` (keep all services of the mixin off the wire) and `accessToken` (token for all services of the mixin).

### 4.2. Members Available in the Mixin

`EntityServerServices<E, PK>` (`sing_server/lib/src/services.dart`) gives you:
- `$query`: the `Query<E, PK>` of the entity for the current call. See [QUERIES.md](QUERIES.md).
- `$entityDef`: the `ServerEntityDef<E, PK>`.
- `$dataRegistry`: the `ServerDataRegistry`.
- `$callContext`: the `CallContext` of the call (prefer the `callContext` parameter).

Methods you can override (they are hooks, not services):
- `$applySearchOnlyFilters(callContext, filters, fields)`: builds the predicate of [extended search criteria](SEARCHES.md). Call `super` and combine with `Predicate.and([...])`.
- `$applyMixinFilters(callContext, filters, fields)`: filter added by generic service mixins. It runs on every standard search, independently of `$applySearchOnlyFilters`.
- `$viewSource(callContext)` and `$resolveViewKeys(callContext, keys)`: give the rows of a view entity. `example/model/lib/model/orders/order_summary.services.dart` shows both.

## 5. Custom Services on a Namespace

A namespace can hold services that do not belong to one entity. The mixin is `on ServerServices`, and you declare it with `@Implementor` on the namespace class:

```dart
// orders.services.dart
import "package:model/model.dart";
import "package:model/sing/server.dart";

mixin OrdersServices on ServerServices {
  Future<int> pendingOrderCount({required CallContext callContext}) =>
      $Order
          .query(callContext)
          .load(where: (fields) => fields.status.$equal(OrderStatus.pending))
          .count();
}
```

```dart
// orders.dart
export "orders.services.dart";

@Implementor(OrdersServices)
class OrdersNameSpace extends ModelNameSpace { ... }
```

`ServerServices` has no `$query`: use `$Order.query(callContext)` and the other generated accessors.

Call it:
- on the server: `callContext.services<Orders$Services>().pendingOrderCount(callContext: callContext)`;
- on the client: `Orders$Services(dataRegistry).pendingOrderCount()`, or `OrderHub$Svc(dataRegistry).orders().pendingOrderCount()`.

A typical namespace service returns aggregates for dashboards: see [CUBE.md](CUBE.md).

## 6. Writing a Service

### 6.1. Rules

A public, non-static method of the mixin becomes a service, unless it carries `@serverSideOnly`. The generator checks these rules:

- **Named parameters only.** A method with a positional parameter is not a service (warning).
- **A parameter named exactly `callContext`** of type `CallContext`. Without it, or with another name, the method is not a service (warning). Make it `required` and put it first.
- **Other parameters**: [auto-jsonifiable types](AUTO_JSON.md). They can be `required`, nullable, or have a default value. The client method copies the default value.
- **Return type**: one of
  - `DataLoader<E>`: rows of an entity (`E` can be another entity than the one that holds the service);
  - `Future<T>` where `T` is auto-jsonifiable, nullable or not;
  - `Future<void>`: no content;
  - `Future<Uint8List>`: binary content (`application/octet-stream`);
  - `Future<HttpResponse>`: the response is sent as is. The client gets the raw `http.Response`.

  Do not return a plain value (`int`, `String`, ...): the generated client method is `async` and does not compile with a non-`Future` return type.

A method that does not follow these rules is still valid Dart. Mark it `@serverSideOnly` (from `sing_core`) to say clearly that it is a helper, or make it private.

### 6.2. Annotations on a Service

| Annotation | Effect |
| --- | --- |
| `@serverSideOnly` | Not a service: a plain server method. |
| `@AccessToken.anonymous`, `@AccessToken.authentified`, any `const AccessToken(...)` | Token required to call the service. See [ACCESS_CONTROL.md](ACCESS_CONTROL.md#23-tokens-on-a-service). |
| `@ActionToken("verb")`, `@ActionToken.read()`, `@ActionToken.write()` | Token derived from the entity token context: `<context path>/<verb>`. |
| `@CompoundToken.all(tokens: [...])` / `.one(...)` | The caller needs all tokens, or one of them. |
| `@OpenApi(false)` / `@openApi` | Remove from, or add to, the OpenAPI document `<mount>/_openapi.json`. It does not change who can call. |
| `@notTraced` (on the method or a parameter) | The value is hidden in traces (passwords, keys). |

A service states at most one token annotation. To combine tokens, use `@CompoundToken`.

### 6.3. Example

From `example/model/lib/model/orders/order.services.dart`:

```dart
mixin OrderServices on EntityServerServices<Order, String> {
  Future<ShippingQuote> quoteShipping({
    required CallContext callContext,
    required ShippingQuote asked,
  }) async => asked;

  DataLoader<Order> addOrder({
    required CallContext callContext,
    required Order$Instance order,
    required Iterable<OrderLine$Instance> orderLines,
  }) {
    return DataLoader<Order>.defered($Order.ofContext(callContext), (
      expect,
    ) async {
      // Business checks go here: stock, required fields, ...
      order = await $Order
          .query(callContext)
          .insertRow(order.$dataRow)
          .exactlyOne();
      for (final line in orderLines) {
        line.order.primaryKey = order.uuid.value;
      }
      await $OrderLine
          .query(callContext)
          .insertRows(orderLines.map((e) => e.$dataRow))
          .execute();
      return $Order
          .query(callContext)
          .loadRef(order.$asReference)
          .withExpectations(expect);
    });
  }
}
```

Use `DataLoader.defered` when a service writes data and then returns rows. The framework runs the loader with the expectations of the caller (fields, resolutions, sort, page), still inside the transaction of the call.

### 6.4. Database Access and Transactions

- `callContext` is the only way to reach the database. One `CallContext` is one database transaction. See [QUERIES.md](QUERIES.md) for queries and their security rules.
- An HTTP call runs in one transaction. It commits when the service returns, and the `DataLoader` it returns is run before the commit. It rolls back when the service throws.
- `callContext.userAccount` is the `Account` of the caller (`uuid`, `displayName`, `tokens`, `tokenGranted(token)`).
- To roll back without throwing (`mustRollback`), run work in a separate transaction (`subTransaction`), or run work after the commit (`afterCommit`), see [TRANSACTIONS.md](TRANSACTIONS.md).

### 6.5. Calling a Service from Server Code

Call the generated services class with the current `callContext`:

```dart
final order = await $Order
    .services(callContext)
    .loadThisKey(callContext: callContext, key: orderUuid)
    .exactlyOne();
```

The call runs in the same transaction. **Access tokens are not checked** for direct server calls: they are checked only when the call comes over HTTP.

### 6.6. Errors

Throw an `AppError` to send a business error to the client: `AppError("orders.errors.noLine", {"order": number}).raise()`. The client receives the same `AppError` (HTTP 400). Any other exception rolls back the transaction and becomes an HTTP 500 without details; this includes database exceptions such as `DbUniqueConstraintException`. See [ERRORS.md](ERRORS.md).

## 7. Entity Change Listeners

To run code on every insert, update, upsert or delete of an entity (defaults, checks, history), write an `EntityControler<E>` that returns `EntityChangesListener<E>` objects, and put it on the entity class as an annotation (`@OrderControler()`). Regenerate the model after adding the annotation. The listeners run inside the transaction of the write.

To react after the commit, in another transaction, send a notification instead.

[NOTIFICATIONS.md](NOTIFICATIONS.md) explains both, with the callbacks each write verb triggers and the pitfalls (upsert runs only the `*Upsert` callbacks, set writes are refused).

## 8. Access Tokens

Each service has one access token, checked against the `Account` of the caller for HTTP calls only. Standard services take the `read` or `write` token of the entity token context (`$Order.tokens.read`, `"/orders/orders/read"`). Custom services take the `@AccessToken...` of the entity or namespace above them (`authentified` in OrderHub). Read the result in the `accessTokens:` map of the generated `Order$Services`.

Sing does not give `AccessToken.authentified` to accounts: add it yourself. Token annotations, token contexts, field tokens and pitfalls: see [ACCESS_CONTROL.md](ACCESS_CONTROL.md).

## 9. Common Issues

### 9.1. Primary Key Type Changed

If the primary key type changes (e.g. `String` to `int`), the mixin `on EntityServerServices<Order, String>` no longer matches. Error pattern:

```
error - order_hub\orders\order.dart:88:15 - 'OrderServices' can't be mixed onto 'EntityServerServices<Order, int>' because 'EntityServerServices<Order, int>' doesn't implement 'EntityServerServices<Order, String>'. - mixin_application_not_implemented_interface
```

What to do:
1. Before rebuilding, change the mixin to `EntityServerServices<Order, Object>`. This is always valid.
2. Rebuild the model.
3. Read the new key type in `_Order$Impl` and fix the mixin declaration.

If service code depends on the key type, comment it out during the rebuild.

### 9.2. Entity Renamed

Renaming `OrderEntity` to `ExternalOrderEntity` renames the generated type `Order` to `ExternalOrder`. The rebuild then fails with `The name 'Order' isn't a type`.

What to do:
1. Find the type `Order` in `common/lib/src/sing/common.dart` (or `model/lib/sing/server_common.dart`).
2. Rename it to `ExternalOrder` **in all packages of the project**, with the IDE rename tool, not with search and replace.
3. Rebuild the model.

### 9.3. A Method Does Not Appear as a Service

Read the `sing_emit` warnings. The usual causes: a positional parameter, no `callContext` parameter, a context parameter with another name, a `@serverSideOnly` annotation, or a mixin not listed in `@Implementor`.
